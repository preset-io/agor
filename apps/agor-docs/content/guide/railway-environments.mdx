# Railway environment reference

The [Compose walkthrough](/guide/environments) keeps everything in YAML. Railway
illustrates the next step: the same environment controls call a small utility
that checks provider state, starts or stops a preview, and reports its URL.

Agor's own repository provides a working reference:

- [`railway-sqlite` in `.agor.yml`](https://github.com/preset-io/agor/blob/main/.agor.yml)
  wires the controls to the script.
- [`launcher.mjs`](https://github.com/preset-io/agor/blob/main/scripts/managed-environments/railway/launcher.mjs)
  implements provider operations, with adjacent tests and volume-reset logic.
- [Railway bootstrap instructions](https://github.com/preset-io/agor/blob/main/.railway/README.md)
  describe the image, service, domain, and persistent volume.

**The preview application in this example is Agor itself.** An existing Agor
instance controls a separate Railway-hosted Agor preview. Hosting Agor on
Railway and using Agor to manage a Railway app are different tasks; for your
own app, replace the bootstrap/runtime details, not Agor's lifecycle interface.

The reference adopts an explicitly provisioned preview for one branch and one
trusted operator. It does not automatically provision a service for every new
branch. Its local lock is not coordination between multiple controllers.

## 1. Prepare a dedicated preview

Use the bootstrap instructions to prepare the service and volume if you are
running the Agor example. Review and adapt its source branch and infrastructure
configuration before applying it: the checked-in configuration targets the
maintainers' preview, not a fresh environment for your account.

Record your own binding in
[`bindings.json`](https://github.com/preset-io/agor/blob/main/scripts/managed-environments/railway/bindings.json):
the Agor branch UUID maps to the exact repository/ref, Railway project,
environment, service, initial volume, and reviewed domain. Set the provider-side
`AGOR_MANAGED_BRANCH_ID` marker to that branch UUID, and ensure the source
variables, mounted volume, and domain match the bootstrap contract. Adoption
is an explicit operator step; Play will not adopt arbitrary resources.

Do not reuse the example's resource IDs, bind two branches to the same
service/volume, or target an environment containing unrelated resources with
the bootstrap IaC. The launcher refuses unknown branches or mismatched
ownership/source/volume/domain state before operating on the preview.

The Agor-specific runtime currently targets the public `preset-io/agor` source
repository. This is reference code to adapt, not a generic arbitrary-repository
deployment installer.

## 2. Supply credentials separately

Configure these through the invoking user's secure global environment-variable
store, never `.agor.yml`, template overrides, or command arguments:

| Variable                      | Purpose                                                                                                                                              |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RAILWAY_API_KEY`             | Environment-scoped Railway project token used by the launcher. Despite this variable's name, it is a project token. `RAILWAY_TOKEN` is its fallback. |
| `RAILWAY_AGOR_ADMIN_PASSWORD` | Unique bootstrap password for the preview app; at least 15 characters and at most 72 UTF-8 bytes. Existing accounts are not reset by changing it.    |
| `RAILWAY_API_TOKEN`           | Separate workspace token, needed only for the optional destructive volume-reset action.                                                              |

Railway distinguishes [project and workspace token scopes](https://docs.railway.com/integrations/api).
Use the narrow project token for ordinary lifecycle work; do not grant the
broader reset credential merely to enable Play. The launcher transfers the
preview password to the app, but does not copy the Railway token into it.

Each caller must have the appropriate credentials. For a shared Agor branch,
agree on a provider owner/sponsor and cleanup responsibility rather than
assuming every collaborator can control the same resource.

## 3. Wire the commands

The relevant shape is below. In Agor's repo, select the existing
`railway-sqlite` variant instead of replacing the whole variant library.

```yaml
version: 2
environment:
  default: railway
  variants:
    railway:
      description: Owned Railway preview
      start: >-
        node scripts/managed-environments/railway/launcher.mjs start
        --repository {{shellQuote repo.github_slug}}
        --ref {{shellQuote branch.ref}} --binding {{shellQuote branch.id}}
      stop: >-
        node scripts/managed-environments/railway/launcher.mjs stop
        --repository {{shellQuote repo.github_slug}}
        --ref {{shellQuote branch.ref}} --binding {{shellQuote branch.id}}
      logs: >-
        node scripts/managed-environments/railway/launcher.mjs logs
        --repository {{shellQuote repo.github_slug}}
        --ref {{shellQuote branch.ref}} --binding {{shellQuote branch.id}}
      app: https://railway.com
```

The command executor needs Node and outbound access to the provider/source
services. This reference uses a pushed GitHub branch, not the controller's
dirty checkout. Have an administrator import the repo configuration, select
the variant in the branch's Environment tab, and **Render** before Start.

`branch.id` is stable resource context; `branch.ref` is the actual Git ref;
`repo.github_slug` identifies the registered GitHub repository. `shellQuote`
passes each string as one shell argument. None is a credential or, by itself,
proof of provider ownership.

## 4. Start, inspect, and stop

**Start** validates the binding, reuses a pending/running deployment when
appropriate or deploys the pushed branch, waits for provider and app readiness,
and emits the discovered App and health URLs. The static Railway dashboard link
is only the fallback. URL reporting uses the same optional
[Start-result contract](/guide/environment-configuration#runtime-urls-from-start)
as any other script; no Railway-specific Agor API is needed.

**Logs** reads bounded provider diagnostics without starting compute.

**Stop** removes the matching GitHub push trigger, drains queued/live
deployments, and waits for an inactive inventory. It preserves the service,
domain, SQLite data, configuration, and caches. Storage can remain billable.
Play does not recreate the push trigger; a later IaC apply can restore it, so
do not apply infrastructure while relying on Stop to keep the preview down.

The optional `nuke` field in the repository's full variant calls the same
launcher with `nuke`. Here Nuke means **reset the owned volume**, not delete the
project: it stops compute, verifies exclusive volume ownership, replaces the
volume, and retains the service/domain. Accounts, credentials, data, and caches
on that volume are erased. Review the bootstrap recovery instructions and
back up data before enabling it. An interrupted reset requires inspection,
not blind repetition. Verify destructive reset with disposable data in your own
setup before relying on it for cleanup.

## Source updates and execution limits

The reference's watch mode polls the pushed branch for source updates. Local
uncommitted changes are not transferred. UI updates can use HMR; backend
changes can restart the daemon. Dependency, startup, and migration changes
require Stop/Play with a new image rather than live synchronization. This is
not a generic Agor Sync action or an exact-revision deployment guarantee.

Watch mode serves this public repository's development source. Do not copy
that exposure model for private source, and keep app authentication enabled:
knowing a public URL must not grant administrative access.

This launcher is intended for standalone execution: its readiness wait can
take up to 18 minutes within Agor's 25-minute standalone command budget.
HA external commands have a five-minute budget. Do not assume this cold-start
flow fits Cloud/HA simply because a warm preview starts quickly. Adapt startup
to the deployment's [execution limits](/guide/environment-configuration#bounded-external-commands-in-ha)
before using it there. The app runs on Railway, not in the command executor.

## Adapt the reference, not its resource ownership

For a different app, keep the lifecycle shape but replace the image, service
configuration, readiness test, and source-update behavior. Static URLs are
enough when your provider address is deterministic; result reporting is optional.

Keep exact ownership checks, bounded waits, secret handling, and a recovery
path for partial allocation. A timeout may leave billable resources running;
inspect the provider before retrying. The local lifecycle lock can also survive
a hard kill: confirm no controller remains active before clearing it. Clean up
the old provider resource before rendering a different variant.

You can keep the adapted utility in your repository and have your agent help
maintain it. Pin the reference revision you adopt, retain its safety tests, and
review changes before giving them provider credentials. There is no separate
runner package to install or provider framework to implement.
