# Boards & Zones

**Boards are 2D spatial canvases for organizing branches.** Like Figma for AI coding work. Drag, group, comment, collaborate in real time.

Instead of linear lists or kanban columns, every [branch](/guide/branches) lives at an `(x, y)` coordinate on a board. Sessions appear as a genealogy tree on the branch card. Multiple users see the same canvas with live cursors.

![Agor board with live collaborator cursors, colorful zones, branch cards, markdown notes, and interactive agent dashboards.](/screenshots/board-hero.png)

_An Agor board staged for an active team: live cursors, roomy workflow zones, branch cards, markdown planning notes, and agent-built dashboards sharing the same canvas._

## Why spatial?

**Your brain remembers space.** You remember:

- "The auth branch is in the top-left corner."
- "Testing sessions cluster on the right."
- "That failed experiment is way down there."

This is location-based memory, the same reason you remember where you parked but forget a shopping list. A 2D board gives every branch and session a _place_. Linear lists discard that.

**Like Figma did for design**, Agor brings spatial collaboration to AI coding:

- Everyone sees the same board.
- Real-time cursors show where teammates are working.
- Drag a branch, teammates see it move instantly.

See **[Multiplayer & Social](/guide/multiplayer-social)** for the full collaboration story (cursors, facepile, comments, attention pulse).

## Zones

**A zone is a spatial region on a board that triggers a templated prompt when a branch is dropped into it.**

Drag a branch into "Code Review" → auto-prompts the agent for review.
Drag into "Needs Tests" → auto-prompts for test generation.
Drag into "Ship It" → auto-prompts for changelog + PR description.

Zones turn your board into a workflow engine. Spatial position _means something_. It triggers behavior.

### Editing a zone

Select a zone to show its compact board toolbar:

- **Rename**, **appearance**, and **lock position and size** cover the common edits.
- **Zone settings** opens on **Automation**, where you configure the prompt and how it starts. **Appearance & placement** contains the name, border and fill colors, label size, and placement lock.
- **More → Arrange** contains the less common layer controls (bring forward/front and send backward/back). When zones overlap, the visually topmost zone is also the drop target.
- **More → Delete zone** removes only the zone. Pinned branches, cards, and comments are unpinned at the same visible board positions; their content and sessions are kept.

Locking a zone prevents moving and resizing it; it does not prevent renaming it or changing its settings. Viewers do not see editing controls. Editors, managers, and the board owner can edit zones.

### How zone triggers work

When you drop a branch into a zone:

1. **Session selection**: which session gets the prompt?
   - **Show picker** (default): choose a session and action when the branch is dropped
   - **Always new**: create a new root session automatically

2. **Templated prompt executes**: the zone's Handlebars template renders with dynamic data from the branch, board, repo, and environment.

### Handlebars template variables

Zone prompts have access to:

- **Branch**: `{{ branch.name }}`, `{{ branch.issue_url }}`, `{{ branch.pull_request_url }}`, `{{ branch.unique_id }}`
- **Board**: `{{ board.name }}`, `{{ board.description }}`
- **Session**: `{{ session.title }}`, `{{ session.description }}`
- **Environment**: `{{ environment.url }}`, `{{ environment.status }}`
- **Repo**: `{{ repo.name }}`, `{{ repo.default_branch }}`

### Example zone prompt

```
Review the implementation of {{ branch.issue_url }}.

Check if:
1. All acceptance criteria from the issue are met
2. Edge cases are handled
3. Error messages are user-friendly

If approved, comment on {{ branch.pull_request_url }} with summary.
```

Drop a branch → auto-prompts with issue and PR links pre-filled. **No copy-paste, no forgetting which ticket this was for.**

## Kanban-style flows

The classic pattern: chain zones into a pipeline.

```
[ Triage ]  →  [ Analyze ]  →  [ Build ]  →  [ Review ]  →  [ Ship ]
   issue          plan           code        cross-agent      PR + notes
                                              review
```

Each zone has a different prompt template. Drag a branch across the board and it walks through the workflow, picking up context at every step.

You can also build asymmetric pipelines: a "Stuck" zone that escalates to a different model, a "Spawn 5 reviewers" zone that fans out to multiple agents, a "Generate tests" zone wired to a Codex template.

## Arranging board content

Agor can arrange mixed-size branches, cards, zones, notes, apps, and artifacts without treating every object as the same-sized tile.

- **Arrange the board:** choose **Arrange board** beside **Fit View** in the main canvas toolbar, review its options, then confirm. **Grid** (the default) derives a photo-style target rectangle from the usable viewport, excluding the canvas controls. Complete rows are justified with one visible gap; the short final row stays left-aligned unless you choose center, right, or justify. **Match/resize zone frames** aligns eligible zone borders while keeping every child at its measured size; turn it off to preserve any already-safe frame. **Compact** instead builds a true two-dimensional heterogeneous cluster by minimizing its largest dimension before area, perimeter, and movement. Geometry and content expansion are independent: **Preserve current expansion** is the default, while **Expand eligible contents** and **Collapse eligible contents** are the only choices that change worktree or body-card density. **Pack zone contents** is on by default: this one-shot operation first packs each eligible zone using its saved Grid/List, columns, and spacing, repairs protruding children, replaces wasteful frames with content-fit frames, and then arranges those final frames beside visible free worktrees, cards, notes, apps, and artifacts. It does not turn on durable **Auto Zone**. Turn packing off to preserve every zone frame, child-relative position, and density while arranging only the outer board. **Fit view after arranging** is also on by default and frames the final eligible whole-board result once, after rendered geometry settles—even when the arrangement was already settled and required no write. Turn it off to preserve the current camera completely for that action. Both choices are local to the open canvas, not saved board settings. Locked or hidden objects and objects inside an ineligible zone stay in place. Frames, children, density changes, and free objects are persisted atomically, and repeating a settled arrangement remains write-free.
- **Tidy a selection:** with the Select tool, drag a marquee from empty canvas or an empty part of a zone. Worktrees, cards, zones, notes, apps, and artifacts can be selected; hold Shift, Command, or Control to add to the selection. Choose **Tidy up** in the selection toolbar for two or more items, including items inside the same zone. Top-level selections use the same Grid/Compact planner as **Arrange board**, but remain centered on their previous bounds. Selecting every eligible top-level object therefore produces the same relative geometry as **Arrange board**; only the documented selection-versus-board origin differs. Unselected free objects, zones, locked items, and protruding children of unselected zones remain fixed obstacles; the selected cluster moves the minimum grid-aligned distance needed to clear them and never displaces them. Selecting only zones changes that action to **Arrange zones** and re-packs the selected zones' own children for their new frames. **Layout options** can request Compact or an exact row-major grid with measured frames and one shared gap, plus an explicit expansion choice that defaults to Preserve whenever the popover opens. Its grid default follows a growing selection up to three columns: seven, eight, and nine objects at three columns always form complete rows of three with only the final row partial, never a width-dependent 2/3/1 pattern. Selecting a whole zone treats its contents as one hierarchy so a group drag does not move children twice. The complete changed-only selection persists as one board layout transaction, and repeating it is a zero-write no-op.
- **Tidy or align a zone:** select a zone, open **More zone actions**, and choose **Tidy up contents**. This remains useful for a single contained item; only an empty zone disables the action. The compact toolbar keeps rename, appearance, lock, and settings visible; Auto Zone, content alignment, direct expansion actions, layer order, and delete stay in the established overflow menu instead of widening the canvas toolbar. Durable Grid/List, spacing, and density policy live in the **Layout** tab of **Zone settings**. Automatic packing reserves the zone's rendered title/status height at the current font size and zoom. Alignment operates on each collision-independent row or column; vertical centering uses the geometric center of the zone rather than shifting contents for its title or status. Pinned branches and cards remain pinned and every supported contained canvas object participates. The toolbar floats above all board objects, including overlapping zones, without changing the zone's saved layer order.
- **Arrange through MCP:** use `agor_boards_auto_arrange` for top-level objects, `agor_boards_auto_arrange_zone` for one zone, or `agor_boards_arrange_zones` for the same content-sized whole-board cluster used by **Arrange board**. The whole-board operation includes visible free items and also re-packs zone children; no follow-up call is needed.
- **Keep the result in view:** the main-toolbar **Arrange board** action follows its local **Fit view after arranging** choice described above. Other explicit **Tidy**, **Arrange zones**, alignment, and selection-layout actions use Agor's smart policy: after a material geometry change, they fit the affected selection only when it would otherwise be clipped or shown at an impractical scale. Already-comfortable and repeated results preserve the camera. Auto Zone maintenance, sorting/realtime updates, remote MCP changes, and reload never inherit the Arrange-board fit request; reload uses only the board's normal initial framing.
- **Maintain a zone:** select one zone and toggle **Auto Zone** directly in its toolbar, or use the same switch in **Configure zone**. The active toolbar button is highlighted and both controls persist through the same zone-configuration path. When an item appears or changes size, the current collaboration lease holder packs it after a short debounce, grows the zone without shrinking its saved floor, and minimally moves only an overlapping chain of unlocked top-level neighbours. The zone, children, and shifted neighbours are one stale-snapshot-guarded transaction and one visible motion; realtime echoes and other tabs do not repeat it. Background maintenance never changes the camera. Multi-zone selection omits the binary toggle rather than implying that every selected zone has the same state.

![Nine selected fictional zones in a compact three-by-three grid beside fixed unselected board objects.](/screenshots/board-selection-grid-fixed-obstacles.png)

- **Collapse one card:** use the collapse button in a worktree or generic-card header. A worktree hides secondary session and environment content; a generic card hides its complete description and note body. Expanded generic-card bodies have one 320px board-space maximum and become a labelled, keyboard-focusable internal scroll region when their exact content is longer. Keeping this bound independent of canvas zoom gives every collaborator the same layout measurement and prevents Auto Zone churn. Collapse removes that whole region while retaining the title and essential header actions, so the same button restores the exact content. Header-only generic cards do not show an inert toggle.
- **Collapse a zone:** select a zone that contains at least one collapsible worktree or generic card and choose **Collapse contents** in its toolbar. Once every capable item is collapsed the button becomes **Expand contents**; a partially collapsed zone still offers **Collapse contents**, so one click makes its capable contents uniform. Zones containing only header-only cards, artifacts, notes, or apps do not show a density control.
- **Compact through MCP:** use `agor_boards_set_compact` to collapse or expand capable worktree/generic-card placements by placement ID, zone, or across a board. Explicit header-only card targets are rejected rather than recording inert presentation state. This is shared board presentation state, so collaborators and agents see the same density.

Density is a board mutation like any other: it needs Board Editor or Manager access, and viewers see no density controls.

![A zone toolbar showing the density control beside Tidy up contents.](/screenshots/board-density-zone-collapse.png)

**Arrange contents** and ordinary Auto Zone maintenance use the same compact-cluster solver as MCP. Every positionable item inside the zone participates: pinned worktrees and cards, plus unlocked artifacts, notes, apps, and supported canvas objects whose centers are inside the zone. A protruding legacy canvas object whose top-left anchor remains inside a too-small zone is also treated as that zone's child, so explicit packing can repair the frame. The solver keeps each measured rectangle at its own size, minimizes the enclosing diameter before area and displacement, and preserves gaps and containment instead of forcing unlike shapes onto row shelves. Repeating an arrangement is a no-op, and sub-grid measurement noise is rounded to the board grid so reload and realtime echoes cannot create churn. Dragging a pinned worktree or card is different: it switches the zone to manual because a move is a durable layout decision.

The browser uses the rendered DOM rectangle. MCP first uses the last browser-measured entity size; an unmeasured worktree uses 500×200, while an unmeasured card uses 380px width and the same bounded body contract as the renderer, so arbitrarily long description/note content cannot manufacture an arbitrarily tall layout estimate. Canvas objects use their persisted rectangle; invalid or missing values fall back to 600×400 for apps/artifacts, 400px width plus a content-derived height for markdown, and 240×120 for legacy text. All values are grid-rounded before packing.

Zone settings provide two opinionated presentations:

- **Grid** uses compact heterogeneous packing when Columns is left on Auto. Choosing a column count is an explicit request for a contained row-and-column layout. Grid preserves the current expansion state unless the separate density policy says otherwise.
- **List** arranges a single readable column. Like Grid and Compact board packing, it never implies a density change.

Each zone separately saves **Content expansion** as Preserve, Expand, or Collapse. Preserve keeps a mixed expanded/collapsed zone byte-for-byte; Expand and Collapse target only worktrees and generic cards with description/note bodies. Header-only cards, artifacts, notes, and apps are never targeted. Missing legacy density fields deliberately normalize to Preserve: existing compact placement state remains unchanged, and changing Grid/List never tries to infer why an item was collapsed.

Both presentations can sort by current spatial order, priority/rank, workflow status, last updated, creation time, or title, in either direction. Switching a previously-unsorted zone to **Auto Zone** defaults to **Last updated · Descending**, so active work appears first. Use **Columns** to request a fixed grid width or leave it on Auto; List hides this irrelevant input because it always has one column. **Spacing** is an exact pixel input shared by UI and MCP. **Grow to fit** lets a tidy or Auto Zone pass expand vertically to contain every row; a manual resize becomes its new floor. **When growth overlaps** then chooses whether to report covered zones or minimally move board zones out of the way, and stays disabled with an explanation while growth is off. Without growth, an impossible tidy reports overflow without moving anything. With Auto Zone off, these arrangement settings remain saved for the next **Tidy up contents** action.

Use **Board settings → Zone defaults** when zones should share one policy. New zones follow that normalized policy deterministically. Existing zones remain explicit overrides until you select **Apply to existing zones**; applying resets them to the displayed policy while preserving their names, prompts, colors, geometry, and locks. In **Configure zone**, **Use board defaults** clearly shows whether one zone follows future board changes. Turn it off to fork an editable override from the current values, or turn it back on to reset and follow again. Reload and realtime updates preserve the same state, and an unchanged save produces no defaults write. MCP uses the same paths through `agor_boards_set_zone_defaults`; `agor_boards_set_zone_layout` accepts `useBoardDefaults: true` for an intentional per-zone reset.

For `agor_boards_auto_arrange_zone`, omitting `columns` uses the compact cluster for pinned entities and geometrically contained canvas objects. Supplying `columns` requests a grid; if that target cannot fit, Agor reports and uses the nearest contained, non-overlapping grid instead of overlapping cards. Set `strictColumns: true` when an exact count must be enforced; then an impossible request returns `applied: false` without moving anything. MCP callers can still request `overflowStrategy: "deck"` explicitly for branch/worktree-only contents. By default, archived cards and branches are excluded so MCP lays out the same visible items as the board. The tool also accepts `preset`, `density`, `sortBy`, `sortDirection`, and `autoResizeHeight`; use `agor_boards_set_zone_layout` to persist those choices, `gap`, and manual or Auto Zone maintenance. `agor_boards_arrange_zones` also defaults its one-shot `density` to `preserve`.

For a whole-board arrangement, `agor_boards_auto_arrange` uses the same compact heterogeneous packing as **Tidy up**; artifacts participate by default, and `includeCanvasObjects: true` also brings text, markdown, and apps into the cluster. Add `includeZones: true` to arrange zones as ordinary fixed-size containers. Pass `columns` only when you explicitly want a row-major grid. Use `agor_boards_arrange_zones` when zone frames should be derived from their measured children: it packs those frames with visible free board items and re-packs each zone's children in the same operation.

## Multiple boards, one workspace

A workspace can have many boards, one per team, one per project, one per long-running initiative. Boards are independent canvases with their own branches, zones, and members.

Common patterns:

- **Per-project boards**: One board per major product, each with its own zones and team.
- **Per-pipeline boards**: A "PR review" board, a "Bug triage" board, a "Roadmap" board.
- **Solo vs team boards**: Personal scratch board for experiments, team board for shipped work.

## Permissions and branch defaults

When branch RBAC is enabled, a board has one primary owner and two intentionally separate permission sections:

1. **Board access** controls who can see and manage this canvas.
2. **Branch defaults** define the complete permission package inherited by branches on this board.

Board access uses Viewer, Editor, and Manager roles. Seeing a branch associated with a board does not make the board visible, and seeing a board does not reveal branch cards the person cannot access.

Branch defaults use the same roles, file-access choices, and session-sharing editor as a branch override. A branch inherits the entire package or overrides the entire package—session sharing never has its own separate inheritance switch.

Entries point to one person or group. Direct person entries override group membership; otherwise group entries combine. **Others** is a clearly labeled fallback for active workspace members who do not match any named entry.

Primary ownership cannot be reassigned. Managers can maintain access and may
enable shared prompting for branch-home Sessions, but do not become owners.
The workspace preference must also be enabled, and execution-home Sessions are
never shareable.
