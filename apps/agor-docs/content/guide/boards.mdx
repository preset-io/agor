# Boards & Zones

**Boards are 2D spatial canvases for organizing branches.** See the work and shape it together: drag, group, comment, and collaborate in real time.

In the spatial view, every [branch](/guide/branches) lives at an `(x, y)` coordinate on a board. Sessions appear as a genealogy tree on the branch card. Multiple users see the same canvas with live cursors.

## Tree and Board views

Use **Tree / Board** at the top-left of a board page to switch between conversation-first navigation and the spatial canvas.

- **Tree** opens by default. **Sessions** lists the primary teammate first, then other teammates, then expandable branches and their sessions. Select a session to open its conversation; on phones, it opens full-screen. Branch details and session actions remain available from the tree.
- **Content** lists artifacts, apps, notes, and cards. Select one to open its content beside the navigator, or full-screen on a phone. **Comments** contains the board discussion.
- **Board** shows the shared spatial canvas without the left navigator. A primary teammate on this board has a labeled card and a **Locate primary teammate** button. If the assigned teammate lives on another board, **Primary teammate** opens it without moving its shared card. Opening a session still opens its conversation alongside the canvas on desktop.

On larger screens, drag the divider between navigation and the open conversation or detail to resize either view. You can also focus the divider and use the arrow keys. Tree and Board remember their split sizes independently.

Your choice of view, split sizes, tree tab, branch order, expanded nodes, and scroll position is remembered for your account and board in this browser. Switching views or sorting the tree does **not** move shared cards, change zone membership, or trigger zone automation. Explicit edits to content and canvas placement remain shared and subject to the same permissions.

Branches default to alphabetical order so they do not move while you work. **Recently updated** uses session update times and branch activity—not exclusively the time of the latest prompt. Teammates stay first in either order. Zone organization and spatial editing remain in **Board** view.

## Why spatial?

**Your brain remembers space.** You remember:

- "The auth branch is in the top-left corner."
- "Testing sessions cluster on the right."
- "That failed experiment is way down there."

This is location-based memory, the same reason you remember where you parked but forget a shopping list. A 2D board gives every branch and session a _place_. Linear lists discard that.

**The space is shared, too.** The same layout that keeps you oriented shows your team where the work stands:

- Everyone sees the same board.
- Real-time cursors show where teammates are working.
- Drag a branch, teammates see it move instantly.

See **[Multiplayer & Social](/guide/multiplayer-social)** for the full collaboration story (cursors, facepile, comments, attention pulse).

## Zones

**A zone is a spatial region on a board that triggers a templated prompt when a branch is dropped into it.**

Drag a branch into "Code Review" → auto-prompts the agent for review.
Drag into "Needs Tests" → auto-prompts for test generation.
Drag into "Ship It" → auto-prompts for changelog + PR description.

Zones turn your board into a workflow engine. Spatial position _means something_. It triggers behavior.

### Editing a zone

Select a zone to show its compact board toolbar:

- **Rename**, **appearance**, and **lock position and size** cover the common edits.
- **Zone settings** opens on **Automation**, where you configure the prompt and how it starts. **Appearance & placement** contains the name, border and fill colors, label size, and placement lock.
- **More → Arrange** contains the less common layer controls (bring forward/front and send backward/back). When zones overlap, the visually topmost zone is also the drop target.
- **More → Delete zone** removes only the zone. Pinned branches, cards, and comments are unpinned at the same visible board positions; their content and sessions are kept.

Locking a zone prevents moving and resizing it; it does not prevent renaming it or changing its settings. Viewers do not see editing controls. Editors, managers, and the board owner can edit zones.

### Zone layout

The **layout** button in the zone toolbar chooses how the zone places its branches and cards:

- **Free** (default): cards stay wherever they are dropped.
- **Row**: cards line up side by side.
- **Column**: cards stack in one column.
- **Grid**: cards fill rows and columns. The zone's width sets how many columns fit, at least two.

In Row, Column and Grid, cards keep their natural height and their order. When an agent adds a session and a card grows, only the cards below it in the same column move. A card dropped into the zone joins at the end. To reorder, drag a card onto the slot where you want it; the other cards shift to make room. Drag a card out of the zone to take it out of the layout.

These zones fit themselves to their cards, so they may overlap a nearby zone. Only a Grid's width can be resized. A badge in the zone's corner shows the layout and card count, and editors can change the layout from it. Switching back to **Free** keeps every card where it was shown. Agents can set a zone's layout with `agor_boards_update` (`layout: "free" | "row" | "column" | "grid"`).

### How zone triggers work

When you drop a branch into a zone:

1. **Session selection**: which session gets the prompt?
   - **Show picker** (default): choose a session and action when the branch is dropped
   - **Always new**: create a new root session automatically

2. **Templated prompt executes**: the zone's Handlebars template renders with dynamic data from the branch, board, repo, and environment.

### Handlebars template variables

Zone prompts have access to:

- **Branch**: `{{ branch.name }}`, `{{ branch.issue_url }}`, `{{ branch.pull_request_url }}`, `{{ branch.unique_id }}`
- **Board**: `{{ board.name }}`, `{{ board.description }}`
- **Session**: `{{ session.title }}`, `{{ session.description }}`
- **Environment**: `{{ environment.url }}`, `{{ environment.status }}`
- **Repo**: `{{ repo.name }}`, `{{ repo.default_branch }}`

### Example zone prompt

```
Review the implementation of {{ branch.issue_url }}.

Check if:
1. All acceptance criteria from the issue are met
2. Edge cases are handled
3. Error messages are user-friendly

If approved, comment on {{ branch.pull_request_url }} with summary.
```

Drop a branch → auto-prompts with issue and PR links pre-filled. **No copy-paste, no forgetting which ticket this was for.**

## Kanban-style flows

The classic pattern: chain zones into a pipeline.

```
[ Triage ]  →  [ Analyze ]  →  [ Build ]  →  [ Review ]  →  [ Ship ]
   issue          plan           code        cross-agent      PR + notes
                                              review
```

Each zone has a different prompt template. Drag a branch across the board and it walks through the workflow, picking up context at every step.

You can also build asymmetric pipelines: a "Stuck" zone that escalates to a different model, a "Spawn 5 reviewers" zone that fans out to multiple agents, a "Generate tests" zone wired to a Codex template.

## Multiple boards, one workspace

A workspace can have many boards, one per team, one per project, one per long-running initiative. Boards are independent canvases with their own branches, zones, and members.

Common patterns:

- **Per-project boards**: One board per major product, each with its own zones and team.
- **Per-pipeline boards**: A "PR review" board, a "Bug triage" board, a "Roadmap" board.
- **Solo vs team boards**: Personal scratch board for experiments, team board for shipped work.

Branches aren't the only thing that can live on a board. **[Cards](/guide/cards)** are generic workflow entities (support tickets, sales leads, content pieces) that an [teammate](/guide/teammates) creates and manages via MCP. Same spatial canvas, same zones, same multiplayer presence, just not git-bound.

## Permissions and branch defaults

Every board has one primary owner and two intentionally separate permission sections. Board and branch RBAC is always enabled:

1. **Board access** controls who can see and manage this canvas.
2. **Branch defaults** define the complete permission package inherited by branches on this board.

Board access uses Viewer, Editor, and Manager roles. Seeing a branch associated with a board does not make the board visible, and seeing a board does not reveal branch cards the person cannot access.

Branch defaults use the same roles, file-access choices, and session-sharing editor as a branch override. A branch inherits the entire package or overrides the entire package—session sharing never has its own separate inheritance switch.

Entries point to one person or group. Direct person entries override group membership; otherwise group entries combine. **Others** is a clearly labeled fallback for active workspace members who do not match any named entry.

Primary ownership can be changed separately by the current owner or a workspace
administrator using **Transfer ownership**. This transfers only the board, not
its branches or their execution identities; see [ownership transfer](/guide/multiplayer-unix-isolation#board-and-branch-permissions).
Managers can maintain access and may
enable shared prompting for branch-home Sessions, but do not become owners.
The workspace preference must also be enabled, and execution-home Sessions are
never shareable.

The primary owner can edit the board's name, emoji, and description independently
of named entries and the **Others** fallback. Other members need Board Editor or
Manager access to edit this metadata. Ownership never grants access across
workspace tenant boundaries.
