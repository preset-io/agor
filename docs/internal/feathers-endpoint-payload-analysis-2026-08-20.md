# Feathers endpoint and payload latency analysis (2026-08-20)

## Status and scope

This analysis starts from one Datadog screenshot from an early Agor Cloud deployment. The panel is a **mean** of `feathers.request.duration_ms` grouped by service, method, and transport. It contains no time window, request counts, percentiles, deployment markers, response sizes, or error split. The values are production observations, not controlled benchmarks.

The current repository was traced and tested on 2026-08-20. It may contain hydration and query improvements that were not in the early deployment. The findings below therefore identify mechanisms and candidates; they do not claim that any one mechanism caused the screenshot.

Per the investigation scope, branch/board authorization predicate construction and RBAC subquery optimization are excluded. Authorization remains an external latency variable. Tenant transaction boundaries are included because they determine PostgreSQL pool occupancy independently of the shape of an RBAC predicate.

## Executive summary

1. The metric measures the outermost Feathers service/hook promise. It includes service hooks, PostgreSQL pool wait and transaction setup/commit, DB work and driver JSON decoding, service enrichment, and outbound/process work awaited by the method. It does **not** measure the subsequent Socket.IO/REST transport write, Socket.IO acknowledgement/client RTT, or MCP response-envelope serialization.
2. The screenshot cannot support causal or capacity conclusions. A mean can be dominated by one cold process invocation, provider outlier, or a handful of startup requests. Counts and p50/p95/p99/max are required.
3. The generic Drizzle adapter often executes `SELECT *` for all candidate rows, parses JSON, then filters, sorts, paginates, and applies `$select` in JavaScript. The nominal generic default and maximum page size are both 10,000, and the client `findAll()` helper auto-pages to the advertised total. `$select` is usually only a wire projection, not a SQL projection.
4. `kb/documents.find` is the clearest unbounded path: the service currently ignores `$limit`, `$skip`, `$sort`, and `$select`. A UI or MCP caller asking for 6 or 10 rows still receives every readable document; `include_content` can hydrate every current version. Its per-document authorization work is excluded from optimization here but remains part of the observed duration.
5. Initial UI hydration starts six background collection reads immediately before a five-request essential batch. On PostgreSQL, each tenant-owned external call normally holds one pool connection/transaction for the full Feathers call. The default pool maximum is 10, so at least 11 near-simultaneous reads can queue even before route-specific work is considered. This is a plausible common explanation for small configuration tables clustering around 2–3 seconds. It is not proven without a production request timeline and pool-wait metric.
6. The isolated measured fix in this change is artifact list projection. The UI already requested only metadata, but the database still returned and decoded `files`. On a PostgreSQL fixture with 500 artifacts and 200 KB of source per artifact, the service metadata list improved from **381.2 ms / 100,335,437 internal JSON bytes** to **13.8 ms / 58,437 result bytes**. Full artifact reads remain unchanged. The MCP list now requests the legacy non-file DTO explicitly.
7. A second, corrected PostgreSQL 17 fixture exercised the repository's **actual** join (`sessions.branch_id -> branches.board_id`) with the production forced-RLS tenant policy: 100,000 sessions across two tenants, 50,000 visible to the request. Across three post-warmup plan runs, the global active-session **page phase** improved from a **35.921 ms median** to **0.298 ms** with `(tenant_id, archived, updated_at)`; representative buffers fell from **16,844 to 172**, with identical 77,400-byte modeled results. The separate exact count retained its prior bitmap/heap plan and varied from 23.1 to 39.4 ms, so it now dominates this service shape. The board-scoped 1,000-row page remained on its existing branch-index plan; an additional tenant+board branches covering index was marginal and was not shipped. Because this deployment is pre-production, lock acquisition is bounded at three seconds and the clear recent-session index is included as an ordinary migration. The earlier direct `sessions.board_id` plan is retained only as a discarded experiment because that column is not populated by current writes.

## What `feathers.request.duration_ms` measures

The app-level around hook in `apps/agor-daemon/src/metrics/feathers.ts` records `performance.now()` immediately before `await next()` and emits the distribution in `finally`. An `AsyncLocalStorage` marker suppresses nested service-to-service calls, so the chart normally represents one outermost external Feathers call rather than double-counting its fan-out.

### Included

- app and service around/before/after/error hooks;
- authentication/password-change checks executed inside the Feathers call;
- the tenant PostgreSQL transaction, including pool acquisition, `BEGIN`, transaction-local `set_config('agor.tenant_id', ...)`, commit, and registered post-commit callbacks;
- repository SQL, exact count queries, row transfer, and driver-side JSON/JSONB decoding;
- JavaScript filtering, sorting, pagination, `$select`, parsing, decryption, and enrichment;
- awaited nested service calls (their time remains inside the outer call even though they do not emit a second metric);
- awaited provider HTTP, OAuth discovery, model/runtime discovery, child-process/executor work, or filesystem work performed inside the method.

### Not included, or not reliably included

- Socket.IO encoding, transport write, acknowledgement callback, and browser/network round trip after the service promise resolves;
- REST response serialization/write after the service promise resolves (the separate HTTP metric records through response `finish`);
- MCP tool schema parsing/ID resolution that occurs before the instrumented service invocation and the final MCP text/envelope rendering that occurs after it;
- actual asynchronous realtime delivery to subscribed Socket.IO channels. `find` emits no mutation event. Mutation calls can include synchronous publication setup/hook work, but delivery is not an awaited end-to-end acknowledgement.

Consequently, a large JSONB column can increase this metric through DB transfer and decoding even when a late `$select` keeps it off the wire. Conversely, expensive transport serialization after service completion will not be visible here.

### Existing tags and interpretation gaps

Existing tags are bounded: `service`, normalized `method`, `transport`, `outcome`, and `status_code`. Two normalizations lose important identity:

- nonstandard methods all become `method:custom`, so the 504.1 ms `users/custom/socketio` row combines unrelated user operations;
- service paths containing characters outside `[a-zA-Z0-9_/-]` become `service:other`. Registered parameterized paths containing `:` can therefore combine in the `other/create` rows.

Socket.IO and MCP rows invoke the same underlying service/hook code, but callers frequently use different query shapes. For example, current UI session hydration asks for `updated_at` order, which can use the SQL page path, while some MCP lists use a shape that falls back to whole-table materialization. Their difference is not evidence of Socket.IO overhead.

### Recommended Datadog views and bounded instrumentation

Always pair the duration distribution with `feathers.requests` count and show p50, p95, p99, and max, separated by success/error. Add deployment/environment/region as normal global tags. Overlay process restart/deploy markers.

Safe bounded dimensions:

- an allow-listed `operation` for custom and parameterized registered services;
- `query_shape`: `global`, `board`, `session`, `recent`, `keyset`, `id-set`, or `other`;
- `projection_shape`: `full`, `metadata`, `without-blob`, `id-only`, or `other`;
- `limit_bucket`: `none`, `1-25`, `26-100`, `101-1000`, `1001-10000`;
- `result_shape`: `single`, `array`, `page`;
- `process_age`: `cold-0-60s`, `warm`.

Do not tag tenant, user, board, branch, session, task, artifact, MCP server, hostname, URL, or raw query values.

Prefer separate distributions/gauges, with only bounded phase/provider-class tags, for:

- DB pool acquisition duration and active/idle/pending pool counts;
- DB transaction duration, SQL duration, and query count per outer request;
- row/result bytes before service projection;
- response serialization duration and response bytes at Socket.IO/REST/MCP boundaries;
- provider/process duration (`openai-embedding`, `mcp-oauth`, `opencode-runtime`, etc.);
- service phases such as `authorize`, `count`, `page`, `hydrate`, `decrypt`, `provider`.

## Common query and hydration behavior

### Generic adapter

For most services, `DrizzleService.fetchData()` calls the repository's `findAll()`. The common behavior is:

1. repository `SELECT *` (sometimes with a small set of pushed predicates);
2. row/JSON conversion;
3. JavaScript filtering and sort;
4. total from the in-memory filtered array;
5. JavaScript skip/limit;
6. JavaScript `$select`.

Generic pagination is `default=10,000`, `max=10,000`. The shared client `findAll()` follows paginated continuation pages until it reaches `total`. A small `$limit` therefore does not necessarily bound database work, and `findAll({$limit: 25})` means “retrieve the entire stable membership in 25-row pages,” not “retrieve only 25.” Tasks/messages have specialized keyset loops, and sessions have a specialized SQL page path for a limited set of query shapes.

### Initial UI request topology

Current `useAgorData` attaches realtime handlers, then starts these non-gated reads:

1. agentic-tool-settings;
2. mcp-servers;
3. session-mcp-servers;
4. gateway-channels;
5. artifacts metadata;
6. mcp-servers/oauth-status.

It then starts an awaited light batch:

7. recent sessions (single page on first load);
8. lean boards;
9. card-types;
10. repos;
11. users.

After resolving the displayed board it starts the board-scoped heavy batch (branches, sessions, board-objects, board-comments, cards, and one full board), then background global hydration for collections that require complete realtime state. Knowledge routes and settings components can add requests. Some global hydration is intentional for realtime correctness; replacing it with a silent hard cap would make the store incomplete.

The default postgres.js pool maximum is 10. Tenant-owned external services usually hold a transaction for the whole call. Therefore the current launch order can queue an essential read behind background work. Reordering/throttling requires a browser test that preserves the quiet-window/generation protections and proves first-paint and eventual global completeness.

## Implemented change

Two isolated changes were implemented: artifact list SQL projection and a recent-session ordering index.

- Added the canonical `ARTIFACT_LIST_FIELDS_WITHOUT_FILES` transport field list.
- Added repository projections:
  - `full` (unchanged default);
  - `without-files` (legacy list DTO without source files);
  - `metadata` (omits source/runtime JSON fields).
- `ArtifactsService.fetchData` chooses a SQL projection only when the caller explicitly supplies a `$select` that excludes `files`.
- Existing callers with no `$select`, `get`, payload/render, publish, export, and mutation paths still retrieve full rows.
- `agor_artifacts_list` now explicitly requests the non-file DTO, so MCP no longer retrieves source blobs merely to strip them after service return.
- Added repository, service, and MCP regression coverage.

This is tenant-safe: the existing trusted tenant transaction/RLS context and board/branch filters are unchanged. Projection only removes columns. No RBAC query construction changed.

- Added PostgreSQL `sessions_tenant_archived_updated_idx (tenant_id, archived, updated_at)` and the single-tenant SQLite mirror `sessions_archived_updated_idx (archived, updated_at)`.
- The PostgreSQL migration starts with `SET LOCAL lock_timeout = '3s'` so lock acquisition fails fast rather than queueing indefinitely. It uses ordinary transactional `CREATE INDEX` because this environment is explicitly pre-production; index construction itself can still block session writes after the lock is acquired.
- The index matches the global recent query and tenant policy. It intentionally does not index the obsolete/unpopulated `sessions.board_id`, and the marginal branches covering index from the controlled comparison was not shipped.
- Response fields, response bytes, counts, hooks, realtime behavior, and RBAC predicate construction are unchanged.
- The migration accelerates only the ordered page in the controlled plan. `findPage` still runs an exact count first; that count did not select the new index and is the largest residual DB phase after the change. The index is therefore not presented as an explanation for the multi-second production mean.

### Index rollout cautions

- The included ordinary PostgreSQL migration is appropriate only because the target is explicitly pre-production. `lock_timeout` bounds lock acquisition, not index build time; once acquired, ordinary `CREATE INDEX` blocks writes to `sessions` until construction finishes.
- For a later large production table, PostgreSQL `CREATE INDEX CONCURRENTLY` cannot run inside the normal transactional migration path. Use a reviewed operational migration/runbook or maintenance window and coordinate the schema declaration.
- The actual board filter lives on `branches.board_id`; current session writes do not populate `sessions.board_id`. Do not add the discarded board-column index based on the first synthetic experiment.
- Exact `COUNT(*)` is not fixed by an ordering index. Where total is not displayed, prefer `limit+1`/`hasMore`; where complete snapshots are required, use keyset iteration.
